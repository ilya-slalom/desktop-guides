# P0 reader and deployment decisions

25 September 2026. The Windows 11 x64 [results](results.md) and [fixture manifest](../../tests/fixtures/p0/manifest.json) are the basis for these choices. The final x64 online package used `1a361aa`; the earlier offline package used `b8d9efc`. This is a reader spike, not the first library release.

| Area | Decision | Evidence and next story |
| --- | --- | --- |
| TXT | Use the native, virtualized line view and normalized UTF-16 character locator for S08. Keep strict UTF-8 with an explicit CP437/Windows-1252 choice on decode failure. | The final x64 `txt-long` run reached first visible text in 902 ms and held 98 realized items for 197,845 lines. Restore returned to line 20 after width and font changes; a Core test covers nearest repeated context after edits. Keep the source text and line index separate from visuals. |
| Static HTML | Use a WebView2 control with staged, manifest-verified files, a fresh profile and synthetic HTTPS origin. Serve each allowed static file from the `WebResourceRequested` handler, deny other requests and navigations, and keep document scripts disabled. | Local CSS/image assets loaded offline. `html-static` and `html-layout` returned to their markers after reflow. Hostile HTML and redirect attempts logged zero canary requests. S09 should provide an explicit, user-initiated system-browser action for trusted external links and a cleanup policy for abandoned temporary profiles. |
| PDF | Retain `Windows.Data.Pdf` only for an image preview and page-position prototype. **Block S10 as a text-accessible PDF reader** until a text-capable engine is selected and tested. | Page 6 restored within 0.02 of the saved page fraction; rendered-image cache peak was 90.1 MiB under its 96 MiB cap. Tagged `pdf-access` has extractable source text, but the rendered image exposes neither a text pattern nor the paragraph to UI Automation. A scanned PDF likewise exposes no document text. Narrator was launched and page controls were keyboard reachable; speech output was not captured. |
| Deployment | Keep the WinUI 3 single-project MSIX, with a framework-dependent Windows App SDK and self-contained .NET. Develop with an unpackaged self-contained copy when needed. | x64 and ARM64 CI packages built; the development-signed x64 package installed, launched and passed 14 fixture workflows online and offline on the Windows 11 host. The passing CI run's x64 MSIX was 64,361,586 bytes. ARM64 CI installed and launched natively, then passed 14/14 UI fixtures. A clean VM must still verify absent-prerequisite failure and recovery before a distribution promise. |

The HTML responder is an intentional change from the technical design's virtual-host folder mapping. Its explicit manifest allowlist, content-hash check and filesystem-link rejection keep each resource request in one audited path. The source guide is never opened by a `file:` URL or modified. P1 must replace the P0 fixture picker with managed library import and preserve these boundaries.

The PDF follow-up should compare WebView2's PDF viewer and a licensed text-capable engine against **all** S10 needs: offline operation, selectable and screen-reader-readable text for a tagged source, search, stable per-page resume, isolated untrusted content and redistribution terms. A raster-only renderer cannot satisfy those needs. No engine is accepted yet; S10 is blocked pending that evaluation. The `pdf-scan` source will still require OCR for actual document text, which is outside P0.

Windows 10 x64 remains `untested` at the user's direction. Native ARM64 Core, install, launch and all 14 reader fixtures passed in CI. The current Windows 11 x64 host had WebView2 and Windows App Runtime installed before the signed test; its offline success does not establish the clean-machine installer route.
